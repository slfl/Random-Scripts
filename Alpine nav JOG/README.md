# JOG Emulator — эмулятор пульта навигации Honda Civic 5D (Alpine / WinCE)

Эмуляция штатного джойстика (JOG) головного устройства навигации Honda Civic 5D
(Alpine AUITK, WinCE 4.2, Renesas SH-4). Позволяет управлять блоком на стенде без
штатного пульта: Arduino держит весь протокол шины и тайминг линии, а HTML-страница в
браузере служит удобным пультом.

> **Важно:** протокол был переосмыслён после реверса прошивки. Раньше JOG считался
> «тупым» односторонним UART с кадром `[тип][маска][маска][cks]` и правилом «сумма=0xFF».
> Это оказалось **неверной интерпретацией захвата**. На самом деле это адресуемая
> шина с квитированием (**AVCLib**), и формат кадра другой (см. ниже).

## Состав проекта

| Файл | Назначение |
|------|-----------|
| `jog_emulator_avc.ino` | Скетч Arduino: протокол AVCLib + бит-бэнг линии + чтение ответа ACK/NAK + мост к ПК (USB **115200**) |
| `jog_control.html` | Пульт в браузере (Chrome/Edge, Web Serial). Прежняя раскладка кнопок + ручная отправка + параметры линии |

Старые файлы (`jog_emulator.ino`, прежний `jog_control.html` с командами `hold/rel/beat`)
устарели — они реализовывали неверную модель протокола.

## Программный стек приёма в навигаторе (результат реверса)

```
провод JOG → внешний коммуникац. контроллер (рег. на внешней шине,
              физ. 0xB8121000 / 0xABF06000 / 0xB8001000)
           → avcbus.dll  ("AVCLib", устройство "HKY1:", приём по прерыванию,
              потоки receive/send/dispatch)
           → hardkey.dll ("HDK", карта клавиш из реестра
              Drivers\BuiltIn\Hardkey\KeyAssign)
           → keybd_event → HMI/UI
```

Источники в прошивке (PDB-пути): `…\ucpfv1xx_bsp\drivers\systemucom\avclib\scif.c`
(avcbus.dll) и `…\ucpfv1xx_bsp\drivers\systemucom\key\hardkey.cpp` (hardkey.dll).

## Протокол шины (AVCLib)

Формат кадра **JOG → навигатор** (подтверждён в валидаторе `avcbus.dll::sub_36035dc`):

```
[0x01] [ID] [LEN] [CKS] [payload × LEN]
  │      │     │     │      └─ полезные данные (LEN байт)
  │      │     │     └─ контрольная сумма = (сумма payload) & 0xFF
  │      │     └─ длина payload (весь кадр = LEN + 4)
  │      └─ идентификатор устройства/сообщения
  └─ стартовый байт SOF, ВСЕГДА 0x01
```

Валидатор проверяет строго по порядку: `frame[0]==0x01` → `frame[2]==(всего_байт−4)`
→ `frame[3]==(сумма payload)&0xFF`. `frame[1]` (ID) используется для маршрутизации к
клиенту и подавления дублей. Любой промах — кадр отбрасывается.

**Ответ навигатора по той же линии:**

| Байт | Значение |
|------|----------|
| `0x06` | ACK — кадр принят и доставлен |
| `0x15` | NAK — ошибка длины/контрольной суммы |

Передатчик при отсутствии ACK повторяет кадр **до 3 раз** («Send data 3times»).
Линия полудуплексная, один провод: передал → отпустил линию → слушаешь ответ.

**Физика линии:** на проводе при включении — **полная тишина** (нет опроса/квитирования
в покое; кадры идут только при действии). Скорость/инверсия/порядок бит окончательно не
зафиксированы — приём идёт через внешний контроллер с нестандартной линией, поэтому эти
параметры **подбираются по ответу навигатора** (команда `SCAN`).

## Идентификаторы (ID)

`hardkey.dll` регистрирует на шине 6-байтовый идентификатор (через `AVCtrl_OpenBus`).
В этой прошивке (дефолт в `.data`) это `06 31 41 34 4B 42` = `0x06` + ASCII «1A4KB», т.е.
принимаемые `frame[1]`-ID:

```
{ 0x06, 0x31('1'), 0x41('A'), 0x34('4'), 0x4B('K'), 0x42('B') }
```

Живая карта кнопок грузится из реестра `Drivers\BuiltIn\Hardkey\KeyAssign`, поэтому
окончательные ID/коды кнопок берутся оттуда, а не из захвата с провода.

> ⚠️ Эти ID **не совпадают** с ранее «прочитанными» `0x80/0x81/0xFF`. Это указывает на
> сбитый порядок бит/сегментацию в старом захвате (либо кнопка кодируется в payload, а не
> в `frame[1]`). Точные ID/payload подтверждаются по ответу ACK (см. рабочий цикл).

## Подключение

```
Arduino (5В: Uno/Nano/Mega)        Головное устройство
  D8  ────[буфер/транзистор]───────  линия JOG
  GND ─────────────────────────────  GND (масса)
```

- Пин данных задаётся в скетче (`DATA_PIN`, по умолчанию `8`).
- **Общая земля обязательна.** Не подавать на линию больше допустимого уровня.
- Линия общая (полудуплекс): эмулятор драйвит её при передаче и отпускает (вход) для
  приёма ответа ACK/NAK.

## Прошивка и запуск

1. Открыть `jog_emulator_avc.ino` в Arduino IDE, выбрать плату/порт, прошить.
2. Закрыть Serial Monitor (порт держит одна программа).
3. Открыть `jog_control.html` в **Chrome** или **Edge** (Web Serial; Firefox/Safari не подходят).
4. «Подключить Arduino» → выбрать COM-порт (скорость USB **115200**).
5. **SCAN** — подобрать параметры линии по ответу ACK, затем нажимать кнопки.

Если страница открыта с `file://` и порт не запрашивается — поднять локальный сервер:
`python -m http.server` → `http://localhost:8000/jog_control.html`.

## Рабочий цикл (как находить верные параметры)

1. Нажми **SCAN** — он перебирает инверсию × порядок бит × скорость и шлёт тестовый кадр,
   ища ответ **ACK 0x06**. Это сразу фиксирует параметры линии.
2. Применяй найденное в блоке «Параметры линии» и жми кнопки, ориентируясь на ответ:
   - **ACK (0x06)** → кадр принят, формат верный;
   - **NAK (0x15)** → байты дошли, но не прошли валидацию (подбирай ID/LEN/payload);
   - **тишина** → байты не доходят (линия / скорость / инверсия / режим выхода).

Навигатор сам подсказывает, что не так — в этом весь смысл реверса протокола.

## Команды скетча (Serial, 115200)

Их шлёт HTML-пульт, но можно и вручную из терминала:

| Команда | Действие |
|---------|----------|
| `CFG?` | показать настройки |
| `CFG bit=208 gap=800 inv=1 msb=0 drive=pp acktmo=25 retry=3 id=80` | задать параметры линии |
| `FRAME <id> <hex payload>` | собрать и послать кадр `01 id LEN CKS payload`, показать ACK/NAK |
| `PL <hex payload>` | кадр с текущим `id` из настроек |
| `RAW <hex bytes>` | послать сырые байты без обёртки (для экспериментов) |
| `BTN <name>` / `BTN?` | предустановленная кнопка / список |
| `MON [ms]` | слушать линию и печатать принятые байты (сниффер) |
| `SCAN <id> <hex payload>` | перебор inv/msb/baud, искать ACK |
| `HELP` | справка |

Параметры по умолчанию: `bit=208` (≈4800 бод), `gap=800` мкс, `inv=1`, `msb=0` (LSB),
`drive=pp`, `acktmo=25` мс, `retry=3`, `id=0x80`.

## Пульт в браузере

- Раскладка повторяет штатный блок: слева MAP / CLIMATE / BACK, в центре джойстик
  (▲▼◀▶, PUSH ENT, кольца ↺CCW / ↻CW), справа MENU / AUDIO / INFO, правее — яркость ☀
  и **«Инженерное меню»**.
- **Инженерное меню** = одновременное удержание **BACK + MAP + MENU** — это один кадр с
  объединённой маской (payload `21 20`).
- Любую кнопку можно удерживать — кадр повторяется (~каждые 120 мс, как штатный JOG),
  отпустил — тишина. Повтор отключается галкой.
- Рядом — блоки «Ручная отправка» (FRAME/RAW/SCAN/MON) и «Параметры линии» (CFG).
- Лог снизу подсвечивает ответ: <ACK> / <NAK> / тишина, автоскролл.

Раскладка кнопок пока несёт прежние маски (lo/hi) как payload — это **стартовая догадка**;
точные значения подтвердятся по ответу ACK и затем будут зафиксированы.

## Как был вскрыт протокол (кратко)

1. Logic-анализатор (Saleae) на линии JOG: захват кадров при нажатиях.
2. Реверс модулей прошивки (`SMGA/`): `hardkey.dll`, `avcbus.dll`, `SCIF.dll`, кусты
   реестра (`default.hv`) — дизассемблер SH-4 (capstone), резолв импортов через
   `coredll.dll`, чтение реестровых блоков.
3. Установлено: hardkey.dll грузит avcbus.dll, открывает «HKY1:», читает кадры
   `AVCtrl_ReadData`, мапит в клавиши и шлёт `keybd_event`.
4. В avcbus.dll («AVCLib») найдено: прямое программирование внешнего SCIF-контроллера
   (VirtualCopy регистров), приём по прерыванию, ACK/NAK (`0x06`/`0x15`), ретрансмит ×3,
   идентификаторы устройств.
5. В валидаторе входящего кадра (`sub_36035dc`) вскрыт точный формат:
   `01 ID LEN CKS payload`, CKS = сумма payload & 0xFF.

## Замечания

- Скорость USB-порта (115200) и скорость линии JOG (~4800) — разные вещи, не путать.
- Эмулятор отпускает линию после кадра, чтобы принять ответ навигатора (полудуплекс).
- Точные ID/payload кнопок и параметры линии финализируются эмпирически по ACK —
  прошивка дала формат и логику приёма, остальное добивается на стенде.
